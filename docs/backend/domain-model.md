# Backend Domain Model

This document maps the **implemented** Domain model. [Architectural Data Model](../architecture/data-model.md) owns conceptual cross-system relationships; [Product business rules](../product/business-rules.md) own approved invariants. Domain classes show representation, not independent approval of future behavior.

| Area | Current Domain representation | Boundary |
|---|---|---|
| Identity and authorization | `User`, `UserRole`, `Role`, `Permission`, refresh, email-verification, and password-reset tokens. | Account and role relationships; Security owns enforcement. |
| Reference data | Country and language concepts. | Shared lookup data, not a Product feature catalog. |
| Nurse and employer | Profile, education, experience, certificate, skill, language, CV, and employer organization concepts. | User-associated business records. |
| Recruitment | Contact-request and candidate interaction concepts. | Distinct from examination and payment ownership. |
| Examinations | Exam/category/version/question content, session, session questions/answers, result/analytics, source/provenance, and standalone access grant. | Session scoring and source representation stay server-owned. |
| Payments | Product, order/order item, checkout session, provider correlation, and fulfillment facts. | An order is not itself an entitlement. |
| Preparation Packages | Definition, immutable published version, offer, materials, practice collection/progress, reporting taxonomy/profile, purchase entitlement/benefit rights, and analytical report. | Package benefits and session/report provenance remain distinct from standalone exam grants. |

`PreparationPackageVersion` binds exact exam, reporting-profile, practice-collection, and material versions. `PackagePurchaseEntitlement` represents a purchase-specific access window and rights. `ExamSession` records source and terminal state; package session provenance connects it to the purchase. These are current class relationships corroborating the approved [Architecture ADRs](../architecture/architecture-overview.md#adr-inventory). Do not derive missing Product rules merely from an entity or enum.

The current examination model distinguishes `Exam` states `Draft`, `Published`, `Archived`; `ExamVersion` states `Draft`, `Published`, `Retired`; and `ExamSession` states `InProgress`, `Submitted`, `Expired`, `Abandoned`. Current admin content handlers require a draft version for question/option mutation, publish a validated draft, and retire a published version; session start selects a published version. A session stores question/option snapshots so later content authoring does not change saved attempt evidence. These are current Domain/Application representations; the Product owner determines required exam behavior.

## Current representation details

- `ContactRequest` snapshots candidate and employer context and stores `Pending`, `Approved`, `Rejected`, or `Cancelled`. Its current create handler checks the employer-profile/nurse-profile pair for an existing `Pending` or `Approved` request, and the database has a matching filtered uniqueness constraint. Transition handlers use conditional updates from `Pending`; the stored status is implementation state, not a new Product rule.
- Current candidate search and contact-request creation require the employer's owned profile and linked organization. The candidate query filters to recruitment-visible nurse profiles whose linked user is active and email-verified, and counts only those filtered rows. The contact-request create handler uses the same eligibility filter; a missing/ineligible target returns the same not-found path. These are current Application query/handler contracts, not independent Product approval of an eligibility policy.
- `PaymentOrder` stores currency and a `long` amount in minor units. Its `PaymentOrderItem` stores product or package-offer purchase-time snapshots, so later catalog edits do not rewrite the order item. The current pending-order constructor sets a 30-minute expiry, while the terminal-status set is `Paid`, `Failed`, `Cancelled`, and `Expired`. These are current Domain values, not a production payment-provider selection.
- Current payment-product catalog queries expose active products; admin handlers archive and restore product activity, and order creation rejects inactive products. Pending orders can be cancelled by their owning nurse and are lazily expired on relevant reads/actions when due. Creating a local pending order alone does not prove payment or grant access; fulfillment is a separate server flow. These are current handler boundaries and must not be read as approval of a production provider.
- `PackagePurchaseEntitlement` owns persisted `PackageBenefitRight` children. Current creation adds one row for each right type, and the database has a unique index on entitlement plus right type. The approved reason for separate persisted rights is recorded in the [entitlement provenance ADR](../architecture/adrs/preparation-package-entitlement-provenance.md).
- `PackagePracticeProgress` stores the latest selected practice option, correctness state (`AnsweredCorrect` or `AnsweredIncorrect`), and UTC answer time for a nurse, entitlement, collection version, and practice item. The current submit handler creates or updates that row using the selected practice option's correctness and requires the entitlement's `PracticeAccess` right. The read handler derives `Unanswered` where no row exists and calculates total, answered, unanswered, correct, and incorrect counts from the purchased collection's items. This is current implementation; [Product business rules](../product/business-rules.md) own approved practice behavior.
- `PackageAnalyticalReport` is a separate persisted report with topic and guidance children, linked by qualifying exam-session identity. The current report retrieval path checks the entitlement's `ReportEligibility` right but uses report existence and a unique session constraint for idempotent generation; it does not consume or mutate the right during generation. This is current backend behavior, not an additional Product report-right rule.

Persistence-specific keys, indexes, and EF mappings are owned by [Storage and Database](storage-and-database.md). DTO and route representations belong to [OpenAPI](../api/openapi.yaml).
