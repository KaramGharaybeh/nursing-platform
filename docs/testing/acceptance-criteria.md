# Acceptance Criteria

Each criterion describes an observable verification condition and points to the owner of the expected behavior or contract. This catalog does not replace that owner or claim an automated test passes. [Testing Strategy](testing-strategy.md) owns verification layers; [E2E Scenarios](end-to-end-scenarios.md) owns cross-boundary journeys; [Security Verification](../security/security-verification.md) owns security-specific checks. No new requirement identifiers are assigned here.

| Authority | Verification condition | Observation boundary |
|---|---|---|
| [Product requirements](../product/requirements.md), [Security authentication](../security/authentication-authorization.md) | Registration, sign-in, email verification, and account/password recovery each produce their approved actor-visible outcome while protected operations require server authorization. | API and browser; security-specific negative cases follow Security. |
| [Product business rules](../product/business-rules.md), [roles](../product/roles-and-permissions.md) | Candidate discovery does not expose nurse contact information before the nurse approves a contact request. | Raw API response and actor journey. |
| [Product requirements](../product/requirements.md), [business rules](../product/business-rules.md) | A nurse can enter a permitted mock-exam session, submit or reach timer finalization, and receive the defined result without crossing access-source rights. | Application/API and cross-boundary journey. |
| [Package rules](../product/business-rules.md) | Package publication fixes included published versions; an offer points to a published version and respects the Product owner's one-active-offer scope. | Domain, persistence, API. |
| [Package rules](../product/business-rules.md) | Successful package fulfillment creates one entitlement per fulfilled order item, starts its access window, and repeated fulfillment does not create a second entitlement. | Persistence/integration boundary. |
| [Package rules](../product/business-rules.md) | An active entitlement blocks repurchase of the same stable package; repurchase after expiry yields a separate purchase, window, attempt, and report right. | API and persistence across the access-window boundary. |
| [Package requirement](../product/requirements.md), [package rules](../product/business-rules.md) | Materials and practice are usable within their access window; practice progress and official exam scoring remain separate. | API and learner journey where delivery is established. Learner material delivery remains an implementation gap. |
| [Package rules](../product/business-rules.md) | A failed package-session start does not consume its attempt; retry of the same source resumes a valid in-progress session, while a conflicting source has the defined deterministic conflict outcome without changing provenance. A session started during access may complete after package expiry under its own timer. | Domain, persistence, API across start/resume/finalization. |
| [Package requirements](../product/requirements.md), [business rules](../product/business-rules.md) | A qualifying finalized package exam session can yield the nurse-owned v1 numeric report with counts, percentages, topic results, and purchased-content guidance; practice answers do not determine it. Qualitative bands are not v1 acceptance conditions. | Domain/report computation, API, actor-visible report. |
| [Package report rules](../product/business-rules.md) | An abandoned session does not qualify; a generated report is unchanged on later reads, remains readable after package expiry, excludes protected exam question detail, and a generation failure leaves a recoverable report right without reversing finalized scoring. | Report persistence/API, raw response, and recovery path. |
| [Product requirements](../product/requirements.md), [Frontend accessibility](../frontend/accessibility.md) | Frontend experiences are assessed against the approved WCAG 2.2 AA outcome using Frontend's verification obligations. | Automated and manual accessibility review. |
| [Product requirements](../product/requirements.md), [roles](../product/roles-and-permissions.md) | Authorized administration can manage Preparation Package promotions at the approved capability level. | Product workflow; discount formula, code format, stacking, and eligibility have no approved rule to test. |

Endpoint field names, status representations, and paths belong to [OpenAPI](../api/openapi.yaml). Route and screen states belong to [Routing](../frontend/routing-and-permissions.md) and [screen contracts](../frontend/screen-contracts/screen-index.md). This catalog does not decide an upstream ambiguity.
